# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

Efficommerce — Sistema de Logística Interna: a suite of 5 independent web tools (label generator, warehouse map, manifest comparator, returns tracker, distributor report) sharing one Supabase database of stores/products. Frontend is vanilla HTML/CSS/JS (no framework, no build step, no bundler). Backend is Vercel Serverless Functions (Node ESM). See `README.md` for the full module/feature breakdown and DB table list — this file focuses on things a coding session needs that aren't obvious from reading one file at a time.

## Commands

There is no build step or linter. Tests (`npm ci && npm test`, node:test): the Mercado y Alistamiento calculation (`public/mercado/mercado-core.js`, uses the `xlsx` devDependency, fixtures in `tests/fixtures/`, anonymized with `tests/anonimizar.mjs`; never commit an export with customer names/addresses/phones), business hours (`tests/horario.test.js`) and API handlers (`tests/stockforge-api.test.js`, `tests/dispositivo.test.js`). The API tests run without network: `tests/simulacion-supabase.js` sets dummy env vars, imports the real client from `api/_supabase.js` and replaces its `auth.getUser`/`from`/`rpc` (every handler shares that object); add new handler tests the same way, never with a real Supabase key.

```bash
npm install -g vercel   # once
vercel dev              # serves /public + /api on http://localhost:3000, same origin
```

Deploy is automatic on push to `main` via Vercel. There's no separate staging/build command — `vercel dev` is also how you manually exercise the API locally end-to-end (real Supabase project required, see `.env.example`).

To change the warehouse-state DB function, edit `supabase/replace_warehouse_state.sql` and **re-run it manually** in the Supabase SQL Editor — there is no migration runner; `supabase-schema.sql` and every file in `supabase/` are applied by hand, and all of them can be re-run safely (idempotent, and they keep the hardened state). **Before running any `.sql` in production: backup + `supabase/remediacion/etapa1/06_VERIFICACION.sql` before and after** (every `regresion_*` row must be OK before; everything OK after). The applied security state and the reference/reversal scripts are in `supabase/ESTADO_PRODUCCION.md` and `supabase/remediacion/etapa1/`. Production once drifted from the repo (36 StockForge policies, including `"Allow all" USING (true)`, existed only in production): never change policies or grants by hand without bringing the `.sql` files in line.

## Architecture

### Five independent frontend modules, one shared layer

Each module under `public/` (`index.*` at root, `stockforge/`, `manifiesto/`, `devoluciones/`, `reporte/`, `mercado/`, ...) is a self-contained HTML+JS+CSS trio with its own global state and its own copy of patterns like modals/toasts — they do **not** import each other. The only shared code is `public/shared/`:
- `api.js` — `apiRequest`/`apiRequestJSON`: fetch + JSON parse + thrown `Error(message)` with `.status` (and `.retryAfter` from the `Retry-After` header). Just removes fetch boilerplate; each module still owns its own auth/token-refresh logic (see below), so don't try to unify those. `mensajeErrorLogin(err)` only turns a failed `POST /api/auth` into the user-facing message (wrong credentials, 429 with wait time, server down, no network); both login modals use it. Don't send the login through `index.js`'s `apiPost`/`apiFetch`: those treat a 401 as an expired session and try to refresh it.
- `dom-utils.js` — `esc()` (HTML-escapes a value), the shared `notify(msg, type, duration, accion)` toast (types: `success|error|warn|info`, aliases `ok/err/danger/warning/inf` map onto them; optional `accion = { texto, alHacer }` adds a button such as "Deshacer", and it returns `{ cerrar }`), `STORAGE_KEYS` constants, `fechaLocalISO()` (local `AAAA-MM-DD` for export filenames — never `toISOString().slice(0, 10)`, which is the UTC date and in Costa Rica gives tomorrow from 18:00 on), and `guardProtectedPage()`/`hasActiveSession()` used by pages other than `index.html` to hide content and redirect if there's no active coordinator session.
- `tokens.css` — the design system: brand/semantic/neutral colors, role aliases (`--color-primary`, `--color-text-muted`…), `--font-sans`/`--font-mono`, text scale (`--text-xs`…`--text-2xl`), 4 px spacing (`--space-1`…`--space-10`), radii (`--radius-sm/md/lg/xl/pill`), shadows (`--shadow-xs…lg`), control heights (`--control-h-sm` 32 / `--control-h` 40 / `--control-h-lg` 48), interaction and z-index tokens, the global `:focus-visible` ring (`--focus-ring`, amber on dark surfaces), `.sr-only`, and `button, input, select, textarea { font-family: inherit }`. Module CSS must not redefine these names (only aliases like `--sans: var(--font-sans)`); `index.css` and StockForge use `--border` as a color, so the stroke tokens are `--border-line`/`--border-line-strong`. `trazabilidad.html` keeps an inline copy (file://) that must be kept in sync. StockForge keeps its own dark palette (themes in `almacen4.js`, each with its own AA `--dim` and `--focus-ring`).
- `componentes.css` — shared components: `.app-header` module header (back + optional logo + `h1` 17 px/600; works with both header markups), `.estado-vacio` (use `estadoVacio({icono,titulo,texto})` from `dom-utils.js` in JS), `.ui-btn`, the `.ui-confirm` dialog and `.icono`. Linked right after `tokens.css` on every page except trazabilidad. Standard buttons: 40 px / radius 10 / 14 px 600 (small 32 px, large 48 px); standard fields: 40 px / radius 10.
- `confirmar.js` — `await confirmar({ titulo, mensaje, aceptar, cancelar, peligro, oscuro })` → `true|false`; native `<dialog>`, focus starts on "Cancelar", a keyboard "aceptar" in the first 300 ms is ignored. Use it instead of `window.confirm()` (all 21 former calls were migrated; the caller must be `async`).
- `a11y.js` — `registrarModal()` (focus trap/Escape/return focus for `<div>` modals), `activarPestanas()`, `sincronizarPresionado()`, `asociarEtiquetas()`.
- `iconos.js` — replaces Font Awesome `<i class="fa-…">` with inline Lucide SVG (including content added later). Manifiesto, Devoluciones, Reporte and Alistamiento no longer load Font Awesome: a new `fa-*` name there must be added to its map (Lucide icons via `lucide-static`). Trazabilidad still loads Font Awesome (file://).

When editing one module, assume nothing you change there affects the others unless it's in `public/shared/`.

### Two coordinator-session implementations that don't share state

Both the label generator (`public/index.js`) and StockForge (`public/stockforge/almacen4.js`) authenticate against the same Supabase user via `/api/auth`, but each keeps its own independent session:
- `index.js`: token in `localStorage` under `STORAGE_KEYS.COORD_SESSION`, refresh token under `effi_coord_refresh_v1` — persists across tabs and reloads.
- `almacen4.js`: token in `sessionStorage` under `sf_coord_token`, refresh token under `sf_refresh_token` — cleared when the tab closes.

Both independently decode the JWT client-side (`atob` on the payload) to check expiry and call `POST /api/refresh` to renew. If you add a new authenticated page, decide deliberately which pattern to copy — don't assume logging in on one page logs you in on another.

### API handler conventions (`api/*.js`)

Every handler is a default-exported `async function handler(req, res)` following the same shape:
```js
setCors(req, res, 'GET, POST, ...');           // from ./_cors.js — no-op unless Origin is in ALLOWED_ORIGIN
if (req.method === 'OPTIONS') return res.status(200).end();
if (!rateLimit(req, res, {...})) return;        // only on public/unauthenticated endpoints (auth.js, refresh.js)
try {
  // GET branches usually run before requireUser() (public read)
  const user = await requireUser(req, res);     // from ./_auth.js — mutating branches only
  if (!user) return;                            // requireUser already sent 401
  // ...method branches, each returns its own res.status(...).json(...)
  return res.status(405).json({ error: 'Método no permitido' });
} catch (err) {
  console.error('...', err);
  return res.status(500).json({ error: 'Error interno del servidor' });
}
```
`_supabase.js` exports both `supabaseAdmin` (the real client, service-role key, no session persistence) and `supabase` as an alias of the same client — either name may show up depending on the file, they're identical. It also exports `selectAll(() => query)`, which pages with `.range()` until an empty page: Supabase silently caps every response at "Max rows" (1000 by default), so any read that must return a whole table (`tiendas.js` GET, `stockforge.js` GET) goes through it. The callback must build a fresh query each call and order by a unique key (end with the PK). `_rateLimit.js` is in-memory per serverless instance (resets on cold start, not shared across instances) — a first line of defense only, not a hard guarantee.

### STOCKFORGE full-state read/replace, not incremental CRUD

Unlike `tiendas.js`/`productos.js` (normal per-row CRUD), `api/stockforge.js` reads/writes the *entire* warehouse in one shot:
- `GET` fires 9 Supabase queries in parallel and reassembles zones/racks/cells/people/tiendas/movements into the nested shape the frontend expects (each rack's cells always get filled in for every bay×level even if empty).
- `GET` is public, but SKU `cost` is only returned with a valid session (`usuarioOpcional` in `_auth.js`; a missing or expired token gets the map without `cost`). The response carries `con_costos`; the frontend sends its token on load and refuses to save a state loaded without costs (saving it would set every `cost` to 0).
- `POST` requires **all** of `almacen-editar`, `tab-add-tienda` and `tab-manage` (`requirePermisos` in `_permisos.js`, the all-of variant), because the function also creates tiendas by name and rewrites `productos.ubicacion`; it sends the whole `{zones, racks, cells, people, tiendas, movements, bodega}` payload to the `replace_warehouse_state` Postgres function, which deletes all 12 related tables and reinserts everything in one transaction, and logs `almacen_guardar` to the bitácora with counts only. There is no partial/incremental save — every edit in StockForge re-saves the full state. StockForge's login (`loginCoordinador`, and a restored session) only enables edit mode when `GET /api/users?accion=yo` grants those three permissions; otherwise the map is read-only, and a 403 on save locks editing without closing the session.
- **Known integrity defects, pending a rework before any intensive use** (do not build on this module without fixing them): the history keeps only the latest 500 `movimientos` per save (DAT-01); the last save wipes other users' changes (DAT-02); a tienda created inside StockForge and assigned before reloading blocks every save (NH-02); consecutive saves from one browser are not ordered (NH-04).
- The frontend (`almacen4.js`) mirrors this: it caches the full state in `localStorage['stockforge_v4']`, renders from cache immediately on load, then fetches fresh data in the background and re-renders (same cache-first pattern `index.js` uses for its own inventory cache under `STORAGE_KEYS.INVENTARIO_CACHE`).
- `skus.producto_id` is the link back to the label generator's `productos` table; saving a SKU with a `producto_id` set also updates that product's `ubicacion`, so its label QR reflects the new physical location automatically.

### Security/DB conventions

- The database is closed to PostgREST: every table has RLS on and **no policies**, and `anon`/`authenticated` have no INSERT/UPDATE/DELETE/TRUNCATE on the main tables; every read and write goes through the API with the service role (which bypasses RLS) and its permission checks. A **new table** must follow the `mercado_*` pattern: RLS on + no policies + `REVOKE ALL ... FROM anon, authenticated`. A **new SQL function**: `REVOKE ALL ... FROM PUBLIC, anon, authenticated`, `GRANT EXECUTE ... TO service_role` and `SET search_path = public, pg_temp`. Never add `USING (true)` or `auth.role() = 'authenticated'` policies: the anon key is public by design, so they open the table to anyone (that was SEC-01/SEC-02, closed on 2026-11-07).
- Every place that inserts DB/user-controlled strings into `innerHTML` goes through `esc()` first (defined once in `dom-utils.js`) — this is the project's only stored-XSS defense, so any new dynamic HTML string must call it too.
- CSP/security headers are centralized in `vercel.json` (`headers` block), not per-page `<meta>` tags. If you add a new CDN script/stylesheet/font, you must add its origin to the relevant CSP directive there or it will be silently blocked in production.
- `manifiesto.js` and `devoluciones.js` are client-side, no database (except: `devoluciones.js`'s "Exportar devueltas" also POSTs the marked guías to `/api/devoluciones`, which records them once each in `devoluciones_registro` with the day's date; the coordinator panel's "Devoluciones" tab in `index.js` reads daily counts via `GET /api/devoluciones` and groups them by week/month client-side) — they parse uploaded Excel (SheetJS `xlsx`, loaded from `cdn.sheetjs.com`) and PDF (`pdf.js` + `Tesseract.js` OCR, from `cdnjs.cloudflare.com`/`cdn.jsdelivr.net`) entirely in the browser. Check `vercel.json`'s CSP whitelist before adding another CDN dependency.
- `public/conteos/` is a public mobile-first page (no session) that POSTs counts to `/api/conteos` (rate-limited, like `devoluciones`); photos are compressed client-side and stored in the private Supabase Storage bucket `conteos`, and `GET /api/conteos` (coordinator only, read by the "Conteos" tab in `index.js`) returns 1-hour signed URLs — hence `https://*.supabase.co` in the CSP `img-src` and `connect-src` (the latter because the tab's "Exportar Excel" fetches each photo to embed it via ExcelJS, lazy-loaded from jsDelivr). Schema/bucket: `supabase/conteos.sql`, applied by hand. The form's "Contado por" list and number of mesas are not hardcoded: they live in `configuracion` (`conteos_personas` as a JSON array, `conteos_mesas`), edited in the coordinator panel > Configuración > "Conteos: personas y mesas", served by the public `GET /api/conteos?accion=opciones` (defaults: 4 mesas and 4 names in `api/conteos.js`), and the POST validates against them (the SQL only enforces `mesa >= 1`). Before saving, `conteos.js` asks for confirmation on valid-but-odd data (expired or >10-year expiry, huge quantities/boxes, more boxes than units, quantity 0, measures over 2.5 m); thresholds are constants at the top of that block. Optional Google Sheets copy: `api/_sheets.js` POSTs each new count to the Apps Script web app in `google/conteos-sheets.gs` (env `SHEETS_WEBHOOK_URL`/`SHEETS_WEBHOOK_SECRET`; one tab per store); failures never fail the save, they leave `en_sheets = false` for the panel's "Enviar pendientes" (`POST /api/conteos?accion=sincronizar`). Print station: counts with `imprimir = true` are polled by the coordinator panel's "Impresión" tab by request time (`GET /api/conteos?accion=por_imprimir&desde=<server ISO from activation>` over `imprimir_solicitado_en`, falling back to `despues_de=<id>` if that column is missing) so transferred old rows that re-request a label are picked up too (`trasladar` with `imprimir: true` resets `impreso_en` and sets `imprimir_solicitado_en`; claimed via `POST ?accion=impreso` which sets `impreso_en` only if null) and printed through the label generator's own `#etiqueta` + `print-single` flow (`imprimirEtiquetaConteo` in `index.js` drives the sidebar selects, prints, then restores them) — so any change to the standard label applies to station prints too. Transfers (`POST /api/conteos?accion=trasladar`, max 5 per call, the panel sends batches) rewrite `tienda_id`/`tienda_nombre`/`producto_codigo`/`producto_nombre`, set `trasladado_de`/`trasladado_en`, log to `conteos_traslados`, and move the Sheets row (delete + add). A partial transfer (`cantidad` < total) instead calls the `trasladar_parcial_conteo` SQL function, which atomically splits the row (new row in the destination with `origen_conteo_id`, sharing `foto_path` — DELETE only removes a photo no other row uses); if that fails `en_sheets` stays false and "Enviar pendientes" always deletes a row from the sheet before re-adding it, so moved or split rows are rewritten instead of being skipped as duplicates.
- `public/recepcion/` (Recepción de mercancía) is a trimmed sibling of Conteos: public page, no session, fields tienda / cajas / recibido por (the Conteos people list from `GET /api/conteos?accion=opciones`) / mandatory photo. It POSTs to `/api/conteos?accion=recepcion` (a branch of the conteos handler because of the 12-function limit; rate-limited + `exigirDispositivo()`), which stores a row in `recepciones` (`supabase/recepciones.sql`, applied by hand) and the photo in the `conteos` bucket under `recepciones/<AAAA-MM>/`. Date/time is editable: the `datetime-local` follows the current Costa Rica time until someone changes it, and only then is sent as `recibido_en` (server rejects future or older than `RECEPCION_MAX_ATRAS_DIAS` = 30 days, and sets `fecha` to that CR day); `creado_en` is always the real registration time, and the dashboard uses `recibido_en || creado_en` (`rcRecibido`) and notes when they differ by more than 10 min. If the `recibido_en` column is missing the insert falls back to server time with `aviso_hora`. The response's `fecha_hora` (Costa Rica time) is what goes into the WhatsApp message ("Ingresa mercancía" / Tienda / Cantidad cajas / Recibido por / Fecha y hora), shared the same way as Conteos (Web Share with the photo, `wa.me` fallback). Coordinator side: panel tab "Recepciones" (`tab-recepciones` permission, default coordinador yes / bodeguero no) reads `GET /api/conteos?accion=recepciones&estado=abiertas|finalizadas|todas` (abiertas = every non-finalized row, no date range; it also returns the server's `ahora` so the browser corrects its clock), registers when the inventory adjustment arrived (`POST ?accion=recepcion_ajuste { id, ajuste_en ISO|null }`, typed as Costa Rica time in a `datetime-local`) and closes it (`POST ?accion=recepcion_finalizar { id, finalizar }`, server time; needs `ajuste_en`; `false` reopens) and can delete a reception with its photo (`DELETE ?accion=recepcion { id }`, trash button on each card, confirm first). All four log to the bitácora (`recepcion_*`). The 24-hour deadline counts **business hours only** (Mon–Fri 7:30–17:00, Sat 7:30–13:00, Costa Rica UTC-6; holidays count as closed days): the math lives in `public/shared/horario-laboral.js` (DOM-free, `globalThis.HorarioLaboral`, tested in `tests/horario.test.js`) and runs in the browser; the DB only stores instants. Holidays: `configuracion.feriados` (JSON `[{ fecha, nombre }]`, edited in Configuración > "Feriados", permission `cfg-feriados`; `/api/config` validates, dedupes and sorts that key), loaded at page start via `loadFeriados(config)` into `HorarioLaboral.setFeriados()`; "Agregar los de ese año" fills the Código de Trabajo list from `HorarioLaboral.feriadosDeLey(año)` (Holy Thursday/Friday from Easter; 2 Aug, 31 Aug and 1 Dec flagged as pago no obligatorio) and the coordinator removes or moves dates before saving. Gauges re-render every 30 s without touching the inputs, and the list reloads every 2 min unless an input is focused.
- Seasonal decoration (screen only, never printed): `public/decoracion.js` mounts the theme's DOM and toggles `body.navidad`/`body.halloween`, styled by `public/navidad.css`/`public/halloween.css` (everything inside `@media screen`, hidden in `@media print`). The theme is global: coordinator panel > Configuración > "Decoración de temporada" saves `decoracion_tema` (`auto`|`halloween`|`navidad`|`ninguna`) in `/api/config`; `auto` picks by date (Halloween Oct 1–Nov 2, Navidad Nov 3–Jan 6).
- The label QR code in `public/index.js` (and the device-linking QR) is generated by an embedded IIFE `QRCode.generate(text, size)` wrapping an unmodified terser-minified copy of `qrcode-generator` 1.4.4 by Kazuhiko Arase (MIT), UTF-8 byte mode, level M, not a CDN — it must keep working fully offline. Don't hand-edit the minified line: an earlier hand-made copy had a stubbed Reed-Solomon step and produced QR codes no reader could decode. To change it, re-minify the npm package (without its UMD wrapper) and verify a rendered code decodes (e.g. `jsqr`).
- Device linking (`api/dispositivos.js`, `api/_dispositivo.js`, `public/shared/dispositivo.js`, table `supabase/dispositivos.sql`, applied by hand): the coordinator panel > Configuración > "Dispositivos vinculados" creates a single-use pairing token (5 min) shown as a QR/link to `conteos/conteos.html` or `devoluciones/devoluciones.html?vincular=<token>`; the page redeems it (`POST ?accion=vincular`) for a credential `<uuid>.<secret>` kept in `localStorage['effi_dispositivo_v1']` and sent as the `X-Dispositivo` header (allowed in `_cors.js`). Only sha256 hashes of token and secret are stored. When `configuracion.exigir_dispositivo = 'true'` (toggle in the same section, default off), the public POSTs of `/api/conteos` and `/api/devoluciones` call `exigirDispositivo()` and answer 403 `codigo: 'dispositivo_no_vinculado'` without a valid credential (and 503 `codigo: 'dispositivo_no_verificado'` if the switch cannot be read: it fails closed); the pages then show a sticky banner (`manejarNoVinculado`). `dispositivos`, like every table, has RLS on with no policies plus `REVOKE ALL FROM anon, authenticated`, so only the service-role API can read it. Any new public write endpoint meant for the warehouse devices should call `exigirDispositivo()` right after its `rateLimit`, and its page should send `headersDispositivo()`.

### Profiles (administrador / coordinador / bodeguero)

The coordinator session has a profile in Supabase Auth `app_metadata.rol` (only the service role can set it). Users without a `rol` (created before profiles existed) count as `administrador` so nobody lost access; users created from the panel always get an explicit one. Per-profile permissions for coordinador/bodeguero are JSON in `configuracion.permisos_roles`; the catalog of keys and their defaults lives in `api/_permisos.js` (`PERMISOS`) and must match `permisosUI()` in `index.js` (tabs `tab-*`, Configuración sections `cfg-*` via `data-permiso` on each `.cfg-sec`, sidebar buttons `nav-<key of NAV_BOTONES>`). `GET /api/users?accion=yo` returns the session's resolved permissions; `index.js` hides what isn't allowed with `.rol-oculto` (separate from the global `.nav-oculto`). Administrador sees everything and is the only one who sees the "Usuarios y permisos" tab (`data-solo-admin`), where it changes profiles (`PATCH /api/users`) and edits permissions with switches (`POST /api/users?accion=permisos`; `/api/config` refuses that key). Server-side enforcement (`requirePermiso(req, res, permiso | [any of])` from `_permisos.js` replaces `requireUser` on coordinator endpoints): `requireAdmin` on all of `/api/users` except `accion=yo`; `/api/config` POST (each key maps to its `cfg-*` section, unknown keys are admin-only); `/api/dispositivos` (`cfg-disp`); `/api/productos` (POST `tab-add-item`|`cfg-json`, PATCH/DELETE `tab-manage`); `/api/tiendas` (POST `tab-add-tienda`|`cfg-json`, PATCH `tab-add-tienda`, DELETE `tab-manage`); `/api/conteos` (`por_imprimir`/`impreso` need `tab-impresion`, the rest `tab-conteos`); `/api/devoluciones` GET (`tab-devol`). A new coordinator endpoint or button should get the permission of the tab it lives in. `/api/stockforge` POST requires `almacen-editar` + `tab-add-tienda` + `tab-manage` (all three; `almacen-editar` defaults to coordinador yes / bodeguero no, and like any key missing from the saved `permisos_roles` it takes its default), and StockForge's login only unlocks editing with them.

Display name: `user_metadata.nombre` (admin edits it inline in the user list, `PATCH /api/users { id, nombre }`; the panel header shows "Hola, <nombre>"). Inactivity logout: minutes per profile in `configuracion.inactividad_roles` (0 = never, allowed values `INACTIVIDAD_OPCIONES`, default all 0), edited in "Usuarios y permisos" via `?accion=inactividad`, delivered as `inactividad_min` with `accion=yo` and enforced only in the browser (`revisarInactividad` in `index.js`): last activity in `localStorage['effi_coord_actividad_v1']` shared across tabs, warning toast one minute before, and an active print station counts as activity. Live permissions: `index.js` re-reads `accion=yo` every 2 min while the tab is visible, on returning to the tab, and right after any API 403 with `codigo: 'sin_permiso'` (`apiFetch` sets `err.codigo`), and tells the user when their profile or permissions changed. Password reset: admin sets a new password for another user with `PATCH /api/users { id, password }` (key button in the user row; one's own goes through Configuración > Cambiar contraseña).

Activity log (`supabase/bitacora.sql`, applied by hand; same no-public-access exception as `dispositivos`): `registrar(user, accion, detalle, datos)` from `api/_bitacora.js` is awaited after each successful change and never throws (missing table only logs to Vercel). Logged: login (`auth.js`), productos, tiendas, conteo transfers/deletes, every `/api/config` POST, dispositivos, and everything in `/api/users`. Action codes are listed in `ACCIONES` there and must match `BITACORA_ACCIONES` in `index.js`; permission labels for the log are the third element of each `PERMISOS` entry. Read by the admin-only "Bitácora" tab via `GET /api/users?accion=bitacora` (filters `desde`/`hasta` ISO, `usuario`, `grupo` = `GRUPOS_BITACORA` prefix set, `q` ilike on `detalle`; 100 per page with `antes=<id>` cursor). New coordinator write endpoints should call `registrar` too.

### Mercado y Alistamiento (`public/mercado/`)

Replaces the Google Sheet "PACKING / CORTE". All business rules live in `mercado-core.js`, a DOM-free classic script that sets `globalThis.MercadoCore` so the page and `tests/mercado.test.js` (via `import`) share it: INVENTARIO = Proveedor + " DS" or Distribuidor (spaces collapsed), TRANSPORTADORA from the numeric "Guía transportadora" (always converted from text) against ordered ranges, UBICACIÓN via ID artículo in the table mapped to that inventario. Defaults (`RANGOS_DEFECTO`, `TABLAS_DEFECTO`) are only fallbacks for the edited ones in the module's Configuración. Excluded rows (`motivos`: anulada, sin_inventario, guía no numérica, cantidad) are left out of the mercado; rows with `avisos` (desconocida, sin transportadora, sin ubicación, tabla no cargada) stay in it but are flagged. The page shows Excel units = mercado units = assigned units. `api/mercado.js` stores each corte as rows (`supabase/mercado.sql`, applied by hand) so it can be audited with SQL: `mercado_cortes` (header/totales/base/validacion), `mercado_lineas` (the mercado; `linea` = index in the list and key of `mercado_alistado`), `mercado_guias` (alistamiento per guía, with destinatario), `mercado_asignaciones` (inventario → persona per corte), plus `mercado_inventarios` and the location tables. Writes go through SQL functions (`mercado_guardar_corte`, `mercado_asignar`, `mercado_reemplazar_ubicaciones`; `mercado_historial` for the list) in one transaction each; large reads use `selectAll`. Like `bitacora`/`dispositivos`, these tables have **no public access** (RLS on, no policies, `REVOKE ALL FROM anon, authenticated`) because `mercado_guias` holds customer names. Rangos/tablas config is `configuracion.mercado_config`. Integrity guards: `POST ?accion=corte` rejects a corte whose líneas, guías and `totales.unidadesMercado` don't add up; the browser sends a per-corte `clave` (UUID) and `mercado_guardar_corte` returns the existing id for a repeated `clave`, so a retried save never duplicates; after upload the page calls `POST ?accion=guias_repetidas` and flags guías already saved in another corte; the alistado poll is discarded if a checkbox save was in flight (`marcasSeq`), so it can't visually undo a fresh mark. Dictionaries keyed by IDs/names use own-property lookups (`MercadoCore.propio`) so an ID like `__proto__` can't leak inherited values. The core finds the header row in the first 20 rows (`filaEncabezados`). The page polls `accion=alistado` every 20 s on "Por persona" so devices see each other's checkmarks. `mercado.html` loads its own CSS/JS with `?v=<date>` (bump it when changing them) and `vercel.json` sends `Cache-Control: no-cache` for `/mercado/*`, because a browser once kept running the old localStorage version. People are not managed in the module: they are the Conteos list (`configuracion.conteos_personas`, read from the public `GET /api/conteos?accion=opciones`) and a person's id is their name (assignments map inventario → name). Printing goes through a dialog (`abrirSelectorImpresion`) that preselects the assigned stores; by default each person's stores go on one combined sheet (`hojasAImprimir`/`hojaSeccionHTML`), unassigned ones one sheet per store. **Access is public like Conteos**: no session needed to read, save cortes, assign, mark alistado and print. Every public write carries `quien` (the "¿Quién eres?" choice, stored in `localStorage['effi_mercado_quien_v1']`) and a saved corte needs `responsable_corte`; the API checks both against the Conteos list (`api/_personas.js`, shared with `api/conteos.js`). Public calls go through `accesoPublico()` (in-memory `rateLimit` + `exigirDispositivo`, also on GETs because of customer names), and the page sends `headersDispositivo()`. Only DELETE corte, `config`, `ubicaciones` and `inventario` need a coordinator session with `mercado-gestion` (the page hides Configuración/Borrar otherwise). `nav-mercado` now only controls the sidebar button per profile. The menu button `nav-btn-mercado` is visible by default (`mostrar_btn_mercado`, default true, not `coord-only`).

### Known stub / inconsistency

**Vercel Hobby allows at most 12 Serverless Functions per deployment** (every `api/*.js` not starting with `_`). There are exactly 12 now. A 13th makes every deploy fail silently from the app's point of view: production keeps serving the last successful build (this happened when `api/mercado.js` was added; the orphaned `api/reporte-tiendas.js` was deleted to make room; it's in git history). Add new endpoints as an `?accion=` branch of an existing handler, never as a new file in `api/`.

## UI copy

- All user-facing Spanish text uses **tú** ("Selecciona", "Ingresa", "Revisa", "Haz clic"): never voseo ("Seleccioná", "Ingresá", "Debés") nor usted ("Seleccione", "Ingrese", "Cargue"), including placeholders like `-- Selecciona --`.
- Dates shown or used as keys/filenames are local (Costa Rica): use `fechaLocalISO()` from `dom-utils.js` instead of hand-rolling `getFullYear()/padStart` or `toISOString().slice(0, 10)`. The only intended UTC uses are Excel serial conversions (built with `Date.UTC` from local parts) and stored instants (`toISOString()` timestamps). `trazabilidad.html` keeps its own inline copy (`localDateKey`) because it must also work opened from `file://`.

## Visual conventions

- No decorative emojis in UI strings, code comments, or markdown. Text labels carry meaning on their own; don't decorate headings, buttons, log messages, or docs with pictographic emoji.
- Functional monochrome glyphs are allowed where they act as plain UI symbols rather than decoration: `✕` (close), `✓` (check/confirm), `☰` (menu), `⚙` (settings). These render as flat, colorless symbols and are treated as icons, not emoji.
- The deliberate exception is the `ICONS` map in `public/shared/dom-utils.js` (`✅` `❌` `⚠️` `ℹ️`) — it powers the shared `notify()` toast system and is the app's actual status-indicator mechanism. Don't strip it, and don't re-embed the same icons inside a `notify()` call's message text (the toast already prepends the right one for `success`/`error`/`warn`/`info`).
